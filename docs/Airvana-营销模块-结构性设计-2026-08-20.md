# Airvana 营销模块结构性设计

> 版本：2026.08 统一结构版  
> 日期：2026-08-20  
> 文档状态：目标架构 / 产品与工程统一基线 / 待分阶段实施  
> 适用范围：Airvana Campaign OS、Agentic Playable 生产与运行、KOL 运营、用户互动、归因、结算、实验和记忆沉淀  
> 非发布声明：本文描述目标能力与实施门禁，不代表相关能力已经集成、上线或取得商业结果  
> 生产真相源：任何具体 Campaign 的目标、地区、预算、奖励、CTA、归因、结算和发布权限，始终以获批的版本化 `Campaign Contract` 为准

## 0. 文档定位与结论

本文作为 Airvana 营销模块的最新通用结构基线，统一此前分散在 Agentic Playable、营销 Agent、AI Brain、Campaign Contract、模型路由、归因、结算、记忆与画像等方案中的设计。

Airvana 的标准产品定义是：

> **Airvana 让每一个 KOL 创作并运营属于自己的 Agentic Playable——一个可持续运营的营销智能体，打通内容生成、互动转化、效果归因、商业结算与数字资产沉淀的完整链路。**

必须保持以下产品关系：

```text
一个 KOL / 用户
  -> 创建并运营多个 Agentic Playable
      -> 每个 Agentic Playable 拥有多个持续迭代版本
```

- KOL 是 Agentic Playable 的创作者、所有者和运营者，不是营销 Agent 本身。
- `Agentic Playable` 是 Airvana 唯一前台营销智能体产品对象。
- “营销 Agent”“运行时智能层”“Memory Service”等名称仅用于内部能力分层，不新增第二个前台产品概念。
- Playable 不是单纯互动素材；Agentic Playable 是受 Campaign Contract 约束、能够持续生成、互动、决策、归因、优化和沉淀资产的营销系统实例。

统一公式：

```text
Agentic Playable
= 受控 Campaign 对象
+ 互动内容与版本
+ 运行时智能层
+ 归因与结算闭环
+ 可持续记忆与策略资产
```

## 1. 设计目标与非目标

### 1.1 设计目标

Airvana 营销模块需要同时实现五个目标：

1. **可生产**：把品牌和 KOL 的自然语言需求转为可验证、可构建、可发布的 Agentic Playable。
2. **会互动**：在 Playable 运行中理解用户、游戏状态、Campaign 目标和环境上下文。
3. **会转化**：在获批边界内选择内容、节奏、CTA 时机和转化表达。
4. **可证明**：通过统一事件、KOL 链接、外部成功事件和可审计归因证明结果。
5. **会进化**：把获批实验、用户记忆、Campaign 复盘和模板经验沉淀为下一版本资产。

### 1.2 非目标

Airvana 营销模块不是：

- 无边界的自动投放或自动媒体采购系统；
- 可以绕过 Campaign Contract 的聊天机器人；
- 自动开户、自动 KYC、自动交易、自动充值或自动连接钱包的执行器；
- 可以自行修改预算、奖励、CTA 目的地、归因规则或结算规则的自治系统；
- 以点击率替代真实业务成功事件的流量优化器；
- 把 KOL、玩家、广告主和平台数据混在一起的通用画像库；
- 把演示数据、供应商案例或模型生成结果描述成 Airvana 已验证业绩的宣传工具。

## 2. 角色、对象与权责

### 2.1 主要角色

| 角色 | 核心责任 | 可以做 | 不可以做 |
| --- | --- | --- | --- |
| 品牌 / 广告主 | 提供商业目标、品牌资产和预算 | 创建 Brief、确认 Contract、审批品牌事实、查看聚合结果 | 读取未经授权的单个粉丝画像；绕过归因和结算证据 |
| KOL | 创作、拥有和运营 Agentic Playable | 选择模板、提交结构化创意、查看自己的项目数据、提出允许字段修改 | 修改锁定商业字段、源代码、归因窗口、结算规则或 Kill Switch |
| 玩家 / 粉丝 | 体验、互动、分享和自主选择 CTA | 控制同意、体验、退出、删除数据、访问获批外部流程 | 因切换视角自动获得 KOL 商业权限 |
| 平台运营 | 审核、发布、监控和处置 | 审核版本、灰度、回滚、暂停、处理争议 | 把未获批内容伪装成生产版本 |
| 合规 / 安全 / 数据审核 | 评估受监管内容和数据用途 | 批准、拒绝、限制地区和设置硬规则 | 将模型自评当作合规结论 |
| 外部系统 | 确认注册、KYC、购买等事实 | 通过获批接口回传成功事件 | 把客户端推测当作确认转化 |

### 2.2 核心业务对象

| 对象 | 作用 | 关键标识 |
| --- | --- | --- |
| Campaign Brief | 结构化需求输入 | `brief_id`, `brief_version` |
| Campaign Contract | 单个 Campaign 的生产真相源 | `campaign_contract_id`, `contract_version` |
| Agentic Playable | 独立营销目标和商业闭环实例 | `playable_id` |
| Playable Version | 同一 Playable 的持续迭代版本 | `playable_version_id` |
| PlayableConfig | 可构建的互动内容和运行策略配置 | `playable_config_version` |
| KOLCreativePatch | KOL 对允许字段提出的结构化创意修改 | `patch_id`, `base_version` |
| Build / Artifact | 确定性构建产物 | `build_id`, `artifact_checksum` |
| Release | 某版本在某范围内的发布记录 | `release_id` |
| Encounter | 某用户在某环境中打开某版本的一次会面 | `encounter_id`, `session_id` |
| Runtime Decision | 运行时在允许边界内做出的决策 | `decision_id` |
| Event | 用户、系统和决策产生的事实记录 | `event_id` |
| Attribution Result | 某成功事件归属于哪个 Campaign/KOL/链接 | `attribution_id` |
| Settlement | 基于 Contract 和归因证据产生的商业账本记录 | `settlement_id` |

### 2.3 新 Playable 与新版本边界

出现以下任一变化，创建新的 `playable_id`：

- 品牌或商业主体变化；
- 核心营销目标变化；
- 主要成功事件或主结算指标变化；
- 目标地区、年龄或合规规则变化；
- 主要受众变化；
- 新的独立商业 Campaign 开始。

以下变化通常只创建新版本：

- 视觉主题；
- 开场、结果卡或分享文案；
- 难度和回合数；
- 玩法细节；
- Contract 允许范围内的 CTA 时机；
- 获批奖励的展示方式；
- 允许字段的实验变体。

## 3. 端到端营销生命周期

Airvana 营销模块的标准链路是：

```text
品牌/KOL需求
-> Campaign Brief
-> Campaign Contract
-> 策略与玩法选择
-> PlayableConfig + 资产清单
-> KOLCreativePatch / 内容生成
-> Schema + Policy + Contract 校验
-> 确定性构建
-> 预览与人工审核
-> 灰度发布
-> Encounter 运行时智能
-> CTA / 外部跳转
-> 外部成功事件
-> KOL归因
-> 商业结算
-> 诊断与受控实验
-> 新版本与记忆沉淀
```

统一生命周期状态：

```text
草稿 -> 待审核 -> 可发布 -> 运行中
-> 待结算 -> 已完成 -> 可复制
```

任何阶段都必须保留：

- 当前 Contract 和版本；
- 审批人和审批范围；
- 构建输入、输出和 checksum；
- 发布范围；
- 回滚目标；
- Kill Switch 负责人；
- 数据、归因和结算证据。

## 4. 总体模块架构

Airvana 营销模块由九个协同层组成。

### L1. Campaign OS

负责目标、受众、渠道、预算、CTA、奖励、归因、结算、审批、数据政策和 Kill Switch。

核心对象：`Campaign Brief`、`Campaign Contract`。

### L2. 创作与运营工作台

面向品牌、KOL、审核员和运营人员，提供：

- Campaign 机会与创建；
- 模板选择；
- 结构化 Brief；
- KOLCreativePatch；
- 预览、审核和版本管理；
- 发布、数据、归因、结算和复盘。

### L3. Agent 编排与生成

由 Brief Agent、Strategy Agent、Generation Agent、Retrieval Layer、Diagnosis Agent 等协作，将结构化输入转为配置、内容和建议。

Agent 只输出：

- 结构化 Brief；
- 策略建议；
- 配置 Patch；
- 内容 / 资产 Patch；
- 诊断与实验建议。

Agent 不直接发布、不直接修改生产代码、不直接改变锁定字段。

### L4. 约束与治理

包含：

- Campaign Contract；
- JSON Schema；
- Constraint Service；
- Policy / Consent / Data Region；
- 角色和 Campaign-specific entitlements；
- 人工审核；
- 审计、灰度、回滚和 Kill Switch。

### L5. Builder 与交付

将模板、PlayableConfig、品牌资产、KOLCreativePatch、语言包、事件策略和运行时策略确定性构建为版本化 H5 / Playable Artifact。

### L6. 运行时智能层

负责用户进入 Agentic Playable 后的：

```text
感知 -> 身份 -> 记忆 -> 决策 -> 生成 -> 行动
```

并由归因回流、效果自优化、分寸与合规、预算 pacing、反作弊、KOL 分身档案和广告主知识库共同支撑。

### L7. 事件、归因与结算

负责统一事件、KOL 专属链接、click ID、外部成功事件、去重、归因窗口、异常量、结算审批和三套独立账本。

### L8. 记忆、知识与数据反馈

沉淀用户记忆、KOL 受众洞察、Campaign 经验、广告主知识、模板表现和实验结果。

### L9. 平台运维与模型治理

包含 AI Gateway、模型注册表、评测、限流、预算、日志、Trace、告警、成本归因、数据备份和事故处置。

## 5. Campaign Contract 与字段控制

### 5.1 权威顺序

发生冲突时，按以下顺序裁决：

```text
已批准 Campaign Contract
> 法律/合规与平台硬规则
> PlayableConfig 字段权限
> 人工审批和发布范围
> KOLCreativePatch
> 模板默认值
> 模型建议
> 运行时优化
```

### 5.2 字段权限

| 类型 | 典型字段 | 控制方式 |
| --- | --- | --- |
| Locked | 法律实体、地区、年龄、预算、奖励、CTA目的地、声明、数据政策、归因、结算、审批、Kill Switch | Contract 版本 + 人工批准；Agent 永不可改 |
| Editable | 标题、语气、获批资产、主题、非实质布局、开场和分享文案 | 结构化 Patch + Schema/规则校验 + 预览审核 |
| Agentic | 获批文案/视觉变体、难度范围、回合数范围、允许状态内的CTA时机、分享卡组合、允许分群推荐 | allowlist + bounds + 实验分配 + 事件 + 回滚 |
| Runtime | session、locale、device、approved region bucket、consent、experiment、fraud/rate-limit | 运行时系统提供，用户或KOL不可伪造 |

每个 Agentic 字段必须同时在 `Campaign Contract` 与 `PlayableConfig` 中声明，不得与 Locked 字段发生父子路径重叠。

### 5.3 失败处理

| 失败类型 | 处理原则 |
| --- | --- |
| 模型超时、缓存 miss、生成格式错误 | 可回落获批 T0 模板，体验继续 |
| 非关键分析、记忆压缩、洞察任务失败 | 异步重试或延迟处理，不阻塞体验 |
| Contract 未批准或版本不一致 | Fail closed，禁止生产或发布 |
| 地区、年龄、授权、数据同意不满足 | Fail closed，停止对应内容、数据读取或 CTA |
| 奖励、结算、归因、金融声明不确定 | Fail closed，转人工审核 |
| Kill Switch、严重欺诈或安全事件 | 立即暂停流量或回滚，不以模板绕过 |

## 6. 运行时智能层

### 6.1 定位

运行时智能层是 Agentic Playable 内部的能力层，不是独立前台产品。它回答六个问题：

1. 感知：当前发生了什么？
2. 身份：这是哪个隐私安全的用户或会话？
3. 记忆：哪些历史事实可以在此 Campaign、此目的下使用？
4. 决策：当前应该做什么，哪些动作被允许？
5. 生成：应该怎样表达？
6. 行动：在哪个 surface 呈现，怎样进入获批 CTA？

### 6.2 CampaignRuntimeContext

运行时的唯一标准输入建议为：

```json
{

  "campaign_id": "cmp_example",
  "campaign_contract_id": "ctr_example",
  "campaign_contract_version": "1.0.0",
  "playable_id": "plb_example",
  "playable_version_id": "1.2.0",
  "playable_config_version": "1.2.0",
  "build_id": "build_example",
  "kol_id": "kol_example",
  "encounter_id": "enc_example",
  "session_id": "ses_example",
  "identity": {},
  "view_role": "player",
  "entitlements": [],
  "consent_state": "granted",
  "region_policy": {},
  "campaign_objective": {},
  "primary_success_event": "registration_complete",
  "approved_agentic_fields": [],
  "memory_pack": {},
  "cohort": {},
  "kol_profile": {},
  "advertiser_knowledge_version": "kb_1.0.0",
  "experiment_assignment": {},
  "fraud_state": {},
  "model_route": {},
  "trace_id": "trace_example"
}
```

客户端只消费服务端裁决结果，不自行决定：

- 可读取哪些记忆；
- 当前用户是否有商业权限；
- 使用哪个模型能力；
- 能否显示某个 CTA；
- 能否进入实验；
- 是否满足地区、年龄、同意和反作弊规则。

### 6.3 RuntimeDecision

运行时决策必须结构化、可审计：

```json
{
  "decision_id": "dec_example",
  "objective": "convert",
  "surface": "result_card",
  "selected_variant_id": "var_example",
  "allowed_patch": {},
  "cta_id": "cta_approved_01",
  "model_capability": "text.fast",
  "evidence": ["evt_example"],
  "policy_version": "policy_1.0.0",
  "contract_version": "1.0.0",
  "fallback": "template_result_v3",
  "expires_at": "2026-08-20T12:00:00Z"
}
```

Runtime Decision Agent 可以决定：

- 选用哪个获批变体；
- 是否引用一条允许的记忆；
- 允许范围内的难度、节奏和 CTA 时机；
- 当前目标是 `convert`、`deepen` 或 `retain`；
- 使用 T0/T1/T2/T3 中哪种生成能力。

它不能决定：

- 产品风险等级；
- 预算和奖励；
- CTA 目的地；
- 地区和年龄资格；
- 归因窗口、优先级和结算事件；
- 发布、支付、开户、KYC、交易或钱包连接。

## 7. 身份、角色与商业权限分离

Airvana 必须把以下四种概念拆开：

| 概念 | 回答的问题 | 是否产生商业权限 |
| --- | --- | --- |
| `identity_tier` | 能否在不同会话中识别同一用户 | 否 |
| `view_role` | 当前展示玩家还是KOL视角 | 否 |
| `kol_active` / creator qualification | 是否通过KOL/创作者资格审核 | 单独仍不足 |
| Campaign-specific `entitlements` | 是否能对特定Campaign执行创建、发布、渠道、归因、结算动作 | 是，且仅限声明范围 |

身份原则：

- 匿名设备、已验证账号和跨设备 person 只做确定性缝合；
- 不使用概率指纹、Canvas、字体或IP相似度自动合并；
- 宁可漏合，不可错合；
- TG、Google、Apple、X、钱包等 provider 通过插件化 verifier 接入；
- 广告主侧 uid 按广告主和应用 scope 隔离；
- 不把一个广告主的 uid、转化和价值解释到另一个广告主；
- 不采集或存储原始 KYC 材料，KYC 由获批外部系统完成并只回传允许的结果状态。

## 8. 记忆与画像系统

### 8.1 记忆原则

```text
事实来自确定性事件系统
含义由规则或模型生成
展示由 Contract、权限、同意和分寸规则控制
```

- LLM 只能增强，不得成为事实真源。
- 每个长期 claim 必须带证据指针。
- 无证据或来源过期的内容不得进入长期画像。
- 记忆是受目的、scope、同意和保留期约束的数据资产，不是可任意跨品牌使用的平台共有画像。

### 8.2 五层记忆

| 层 | 内容 | 真源 / 存储职责 | 用途 |
| --- | --- | --- | --- |
| L0 事件日志 | 原子行为、选择、时延、surface曝光、CTA、决策应用 | append-only 事件真源 | 回放、归因、审计、重建 |
| L1 会话工作记忆 | 当前局状态、游戏变量、已展示内容 | 客户端/运行时短期状态 | 局内自适应 |
| L2 会话小结 | 人格、特质向量、关键时刻、下次 hook | 规则优先，模型只压缩表达 | 下次返场与L3合并 |
| L3 长期 claims | 慢变特质、关系、已授权转化状态 | 结构化真源 + 热读副本 | 个性化与目标切换 |
| L4 群体聚合 | KOL受众、Campaign cohort、全局基线 | 去标识聚合 | 冷启动、洞察和比较 |

### 8.3 MemoryClaim

```json
{
  "claim_id": "clm_example",
  "privacy_safe_user_id": "usr_hash",
  "key": "interaction_patience",
  "value": 7,
  "confidence": 0.72,
  "evidence_event_ids": ["evt_01", "evt_02"],
  "scope": "kol:kol_example",
  "purpose": "playable_personalization",
  "consent_version": "consent_1.0",
  "campaign_contract_version": "1.0.0",
  "observed_at": "2026-08-20T10:00:00Z",
  "expires_at": "2027-02-16T10:00:00Z",
  "status": "active"
}
```

写入规则：

- 先用规则评价意外性、决策揭示性、商业相关性和身份稳定性；
- 低价值噪音只保留在L0，不进入L3；
- 冲突按时间和证据权重合并，同时保留有限漂移历史；
- 置信度随重复证据上升，随时间衰减；
- 转化相关 claim 必须按广告主 scope 隔离。

读取规则：

- 单人结构化画像优先 schema-first 整包读取；
- 读取前执行 scope、purpose、consent、contract、region、TTL 和 taboo 过滤；
- 自由文本对话未来可单独增加检索层，不把特质画像强行改造成向量库；
- `memory_pack` 只返回本次决策允许使用的最小信息。

遗忘与撤回：

- 用户可撤回个性化同意或发起删除；
- 删除热读副本、claims、会话小结和可识别身份边；
- 在允许保留聚合价值的前提下匿名化原始事件；
- 删除、冻结、撤回和恢复均需审计；
- 被遗忘或低于置信阈值的内容不得出现在读路径。

### 8.4 群体基线

群体比较必须满足：

- 指标来自受控词表；
- scope 只允许预定义的 KOL、Campaign 和全局层级；
- 有明确分母、时间窗和更新时间；
- 样本达到 Contract / 数据政策要求；
- 只有真实 `measured` 数据可以对用户表达比例、多数或少数；
- `seeded`、编辑估计或测试数据只能用于内部冷启动，不得作为用户可见社会证明；
- 数字由确定性系统填充，LLM 不生成统计数字。

## 9. 生成、模型路由与成本

### 9.1 四档生成

| 档位 | 定位 | 典型用途 | 失败处理 |
| --- | --- | --- | --- |
| T0 | 获批模板，无实时模型 | 首访、低价值流量、所有失败兜底 | 永远可用 |
| T1 | 一次生成整局个性化台词包 | 开场、幕间点评、对比句 | 超时或坏输出回T0，不阻塞 |
| T2 | 高价值高光内容 | 结果卡、分享文案、重要解释 | 超时回获批结果模板 |
| T3 | 用户主动触发的对话 | 转化助手、FAQ、异议处理 | 无依据则拒答或转人工 |

### 9.2 路由顺序

模型路由按以下顺序执行：

```text
Contract / approval / allowed fields
-> data region / retention / consent
-> risk level and required capability
-> task-level evaluation admission
-> model health / quota / budget
-> quality / reliability / latency / cost scoring
```

业务代码只使用稳定能力别名，例如：

- `text.fast`
- `text.balanced`
- `text.reasoning_code`
- `image.generate`
- `embedding.default`

不得在业务规则中写死供应商、模型名称、价格或促销期。

### 9.3 延迟与缓存

- T1 默认每局一次生成整包，而不是逐回合调用；
- 利用封面、动画和结果翻牌作为异步预取窗口；
- 台词包按 KOL voice、语言、返场类型、persona 和场景桶缓存；
- per-user 信息只通过安全槽位插值，不进入共享缓存明文；
- 迟到但仍有效的结果可以写缓存供后续使用；
- 记忆压缩、受众洞察、桶预热和离线评测走异步队列；
- 每次调用记录 task、模型部署、版本、token、成本、路由原因、Contract 和 trace。

### 9.4 预算治理

至少设置：

- Campaign 日预算；
- 单用户 / 单会话模型成本上限；
- 单模型、单供应商和单地区配额；
- 超时和熔断；
- 成本归因到 Campaign、Playable、版本、Agent、任务和成功事件；
- 当合规与Contract允许时，模型超预算可回T0；
- 不得因节省成本而绕过更高风险任务所需的合规模型、独立校验或人工审批。

## 10. 知识资产

### 10.1 KOL 分身档案

KOL 分身档案是 Agentic Playable 的表达资产，包含：

- 获批身份、名称和头像；
- 人设、语气、语言、口头禅；
- 允许与禁止话题；
- 肖像、声音和内容授权及有效期；
- 受众聚合先验；
- 版本和审批记录。

KOL 分身档案不能代替 KOL 商业资格，也不能自动把一个 KOL 的授权转移到另一 Campaign、地区或渠道。

### 10.2 广告主知识库

广告主知识库是品牌事实和答疑的唯一获批来源，包含：

- 产品和服务事实；
- FAQ；
- 流程、费率、限额和资格说明；
- 获批声明和禁用声明；
- 异议处理策略；
- CTA 与外部流程说明；
- 证据来源、版本、地区、有效期和审批状态。

规则：

- 知识库答不出时承认不知道，不允许补造；
- 过期、未批准或跨地区知识不得进入生成上下文；
- 受监管信息需记录法律实体、目标地区、推广活动和审核证据；
- 模型输出不能被当作广告主事实反写知识库。

### 10.3 Campaign、模板与策略记忆

分别沉淀：

- Campaign 特定实验和诊断；
- KOL 与受众关系洞察；
- 模板在特定场景的表现；
- 可复用但需重新审批的策略模式。

实验赢家默认只对当前 Campaign、版本和声明的 segment 有效，不自动升级为平台通用规则。

## 11. 行动 Surface 与转化边界

运行时智能层可以附着在多个 surface：

| Surface | 作用 | 主要输入 | 主要约束 |
| --- | --- | --- | --- |
| 局内说书人 | 解释行为、保持沉浸 | T0/T1 台词包 | 分寸、频控、禁词 |
| 结果卡 | 人格反馈、分享与桥接CTA | T0/T2内容 | 不作金融建议，不暴露敏感行为 |
| CTA组件 | 展示获批价值和下一步 | RuntimeDecision、Contract CTA | 目的地和状态锁定 |
| 转化助手 | 用户主动答疑和异议处理 | memory_pack、广告主知识库 | T3仅用户主动触发；不自动执行外部动作 |
| TG/站内对话 | 局外持续互动 | 对话记忆、KOL档案 | 同意、频控、人审和渠道授权 |
| KOL洞察卡 | 展示受众聚合和建议 | L4、Campaign诊断 | 不显示单用户画像；小样本不展示 |

边界：

```text
运行时智能层决定“说什么、何时说、使用哪个获批变体”
Playable负责“展示和交互”
归因模块负责“这一跳怎样被记录和确认”
结算模块负责“什么结果可以进入商业账本”
```

任何 surface 都不得：

- 自动开户、KYC、交易、充值或购买；
- 通过游戏人格推断用户适合更高风险金融产品；
- 使用未获批的紧迫感、倒计时或社会证明；
- 隐藏赞助、资格、风险、奖励或到期条款。

## 12. 事件、归因与三套账本

### 12.1 标准事件信封

每个事件至少包含：

```json
{
  "event_id": "evt_example",
  "event_name": "agent_decision_applied",
  "event_time": "2026-08-20T10:00:00+08:00",
  "tenant_id": "tenant_example",
  "campaign_id": "cmp_example",
  "campaign_contract_id": "ctr_example",
  "contract_version": "1.0.0",
  "playable_id": "plb_example",
  "playable_version_id": "1.2.0",
  "build_id": "build_example",
  "creative_id": "cr_example",
  "channel_id": "ch_example",
  "kol_id": "kol_example",
  "link_id": "link_example",
  "session_id": "ses_example",
  "encounter_id": "enc_example",
  "decision_id": "dec_example",
  "privacy_safe_user_id": "usr_hash",
  "consent_state": "granted",
  "region": "HK",
  "experiment_id": "exp_example",
  "variant_id": "var_example",
  "properties": {}
}
```

禁止在事件属性中写入姓名、邮箱、电话、钱包秘密、原始KYC资料、认证Token或目的地密钥。

### 12.2 最小事件词表

P0–P1至少支持：

- `impression`
- `play_start`
- `valid_interaction`
- `choice`
- `agent_decision_applied`
- `level_start`
- `level_complete`
- `play_complete`
- `play_fail`
- `replay`
- `result_view`
- `share`
- `cta_view`
- `cta_click`
- `consent_granted`
- `error`

外部系统确认后才允许写入：

- `lead_submit`
- `registration_complete`
- `kyc_complete`
- `purchase`
- `reward_eligible`
- `reward_claim`

客户端点击、回调或页面打开不能伪装成确认注册、KYC、购买或结算成功。

### 12.3 KOL归因

每个获批 Campaign、KOL、渠道和创意生成唯一、可撤销的链接或代码，至少携带：

```text
campaign_id, creative_id, channel_id, kol_id, link_id
```

归因流程：

1. 校验 Campaign、KOL、链接和发布范围；
2. 创建隐私安全的服务端 click ID；
3. 在获批窗口内保留允许的关联；
4. 接收外部系统签名或核验后的成功事件；
5. 执行窗口、优先级、去重、地区、欺诈、撤销和退款规则；
6. 单独写入归因结果；
7. 再由结算系统根据 Contract 判断是否可结算。

### 12.4 三套独立账本

| 账本 | 记录什么 | 不等同于什么 |
| --- | --- | --- |
| 玩家权益账本 | AIP、优惠券、资格、站内权益和履约状态 | 不等同KOL收入或品牌结算 |
| KOL归因账本 | 哪个KOL/链接/版本产生了哪个合格结果 | 不等同已支付收入 |
| 品牌商业结算账本 | Contract主结算事件、金额、审批、争议、付款状态 | 不等同玩家积分或AIT通用Token |

身份、关注数、订阅、AIP、AIT、KYC 或 `view_role` 都不能替代 Campaign-specific 商业 entitlement 和结算证据。

## 13. 效果自优化与实验

### 13.1 优化对象

优先级建议：

```text
CTA价值表达与时机
> 开场 hook
> 结果卡与分享文案
> 难度和回合节奏
> 对比句措辞
```

只能优化 Contract 中声明的 `allowed_experiment_fields`。

### 13.2 line_stats

运行时记录：

```text
Campaign + Playable Version + Segment + Surface
+ Variant ID + Exposure + Valid Interaction
+ CTA Click + Confirmed Success Event + Guardrails
```

近端指标可以使用 CTA 点击或完成率，但远端主判断必须使用 Contract 的主要成功事件和质量指标。

### 13.3 实验门禁

每个实验必须记录：

- 假设与因果理由；
- 随机化单位和稳定分配规则；
- control / treatment版本；
- 允许改变的字段；
- 主指标、护栏指标和排除规则；
- 样本与决策规则；
- 开始、暂停、结束和回滚负责人；
- 隐私、地区和分群限制。

实施顺序：

1. 先运行确定性的 T0 A/B；
2. 数据质量、样本和归因稳定后，再使用 bandit；
3. bandit 只能选择已批准变体；
4. 合规、隐私、欺诈、成本或主护栏失败时立即停止；
5. 实验结果只对声明范围有效，未经复验不得跨Campaign推广。

## 14. 隐私、分寸与受监管场景

### 14.1 个性化分寸

- 只引用用户在获批产品范围内产生的行为；
- 说可解释的体验判断，不暴露时间戳、设备型号、精确次数等监控感信息；
- 负面转化事实可以内部影响策略，不直接对用户说；
- 跨Campaign只使用获批的抽象特征，不暴露另一Campaign具体行为；
- 默认每局最多两次显式记忆引用；
- 用户必须能关闭个性化并发起遗忘；
- KOL和广告主只看权限内聚合，不读取单个粉丝档案。

### 14.2 禁止的个性化

- 根据游戏行为推断并推荐更高风险金融产品；
- 个性化投资建议或收益承诺；
- 把娱乐人格测试包装成金融适当性判断；
- 使用 fabricated social proof、种子数据或小样本比例影响决策；
- 针对不符合年龄、地区或资格的人群展示受限CTA；
- 收集私钥、助记词、原始KYC资料或非必要PII；
- 未经明确用户动作自动连接钱包、开户、KYC、交易、充值或购买。

### 14.3 Web3 / 受监管Campaign

生产前必须明确：

```text
具体法律实体 x 适用监管/牌照
x 被推广服务或活动 x 目标地区 x 推广方式
```

未解决的金融推广、KYC导流、交易、充值、钱包、真实加密奖励或结算问题必须转人工法律/合规审核，不能以模型免责声明代替批准。

## 17. 分阶段落地路线

### P0：Contract与事件地基

范围：

- 一个品牌 / 买方；
- 一个获批Campaign；
- 一个KOL；
- 一个Agentic Playable；
- 一个运行版本；
- 一个主要成功事件；
- 一条从运行到外部确认或明确止于CTA的真实证据链。

建设：

- Contract、Playable、版本和事件绑定；
- 统一事件信封；
- Runtime session与`agent_decision_applied`；
- consent、region、identity、entitlement和Kill Switch；
- 移动端/Playable真实调用服务端，而非只写本地状态；
- 基础回滚与审计。

退出条件：

- 一局可按事件重放；
- 无Contract或无权限时动作被拒绝；
- 事件完整、去重和版本一致；
- 运行版本可暂停并回滚。

### P1：零LLM记忆验证

建设：

- 确定性身份；
- L0–L3基础记忆；
- evidence-backed claims；
- memory_pack；
- T0模板返场问候；
- 无记忆对照组；
- 个性化关闭和遗忘。

验证：

- 返场完局率；
- 返场CTA率；
- 用户退出和投诉；
- 串人、串Campaign和无证据记忆必须为0。

只有确认记忆产生正向价值，才进入大规模生成。

### P2：受控个性化生成

建设：

- T1整局台词包；
- T2结果卡；
- 桶化缓存；
- AI Gateway和能力别名；
- KOL分身档案；
- measured群体基线；
- Schema、Contract、Policy和Evidence门禁。

验证：

- 完局、分享和主要成功事件对照；
- 回退率、时延、缓存和成本；
- 无依据claim、违规表达和敏感信息泄露必须为0。

### P3：归因回流与目标切换

建设：

- KOL专属链接和click ID；
- 外部成功事件；
- 转化去重和证据；
- `convert -> deepen -> retain`目标切换；
- 已转化用户CTA抑制；
- 三套独立账本。

验证：

- 外部确认匹配率；
- 归因异常率；
- 不重复拉新；
- 结算只接受Contract定义的合格事件。

### P4：受控自优化与知识库

建设：

- line_stats；
- T0 A/B；
- 允许字段内的bandit；
- 广告主知识库；
- T3用户主动答疑；
- KOL聚合洞察和Campaign诊断。

验证：

- 实验样本和数据质量；
- 主要成功事件提升；
- 护栏不恶化；
- 结果不越Campaign泛化。

### P5：规模化与生产治理

建设：

- 多品牌、多地区、多语言、多渠道；
- Provider和模型动态注册；
- 生产数据库、队列、对象存储、备份和密钥管理；

## 18. 当前实现状态与证据边界

截至2026-08-20的代码实测基线：

- 移动端仍主要是本地演示应用；
- 服务端是测试覆盖较好的本地状态机；
- 移动端与服务端营销主链未集成；
- 真实运行库中的 Campaign Contract、归因、权益和商业账本缺少真实业务记录；

## 19. 统一术语

### 19.1 必须使用

- “让每一个KOL创作并运营属于自己的Agentic Playable”；
- “KOL是创作者、所有者和运营者”；
- “Agentic Playable是营销智能体”；
- “一个KOL可以拥有多个Agentic Playable”；
- “Campaign Brief -> Campaign Contract”；
- “Runtime Decision Agent只能修改获批Agentic字段”；
- “玩家权益、KOL归因和品牌商业结算是三套独立账本”。

### 19.2 禁止或废弃

- “一个KOL就是一个营销智能体”；
- “KOL本身是Agent”；
- 把Creator Room、KOL Room、Activation作为第二前台产品；
- 把`view_role`、KYC、订阅、粉丝数、AIP或AIT等同商业权限；
- 把CTA点击等同确认转化；
- 把AIT描述成自由流通或可自由交易Token；
- 把演示数据、目标架构或模型估算描述成已上线业绩。

## 20. 最终验收标准

Airvana 营销模块只有同时满足以下条件，才可被描述为完成：

1. Brief、Contract、Playable、版本、构建、发布、事件、归因和结算引用同一条版本链；
2. Locked / Editable / Agentic / Runtime字段权限有服务端强制校验；
3. KOL商业动作由Campaign-specific entitlements控制；
4. Playable真实上报统一事件，能够回放关键用户和Agent决策链；
5. 外部成功事件由获批系统确认并完成去重与归因；
6. 玩家权益、KOL归因和品牌结算账本分离；
7. 记忆有证据、scope、purpose、consent、TTL和遗忘机制；
8. 模型可失败降级，但Contract、合规、权限和安全不能被降级绕过；
9. 实验只改变获批字段，并以Contract主要成功事件和护栏评估；
10. 生产版本通过移动、功能、事件、性能、隐私、失败路径、灰度和回滚验证；
11. 当前状态、外部依赖和未验证项被如实标注；
12. 可回答完整证据问题：

```text
谁
在什么Campaign、Playable、版本和环境中
看到了哪一个Agent决策或内容变体
做了什么
之后发生了什么
结果由哪个系统确认
归因和结算依据是什么
```
