# Airvana 未完成功能闭环审计

> 版本：v2.0 当前事实版  
> 审计日期：2026-08-15  
> 项目：Airvana v5.3 / Loopit v2 高保真全栈本地 MVP  
> 文档状态：待产品确认；确认前不继续扩展功能开发  
> 审计范围：移动端 `/`、Workspace `/workspace`、Node.js + SQLite 本地服务、iOS/Android 演示壳、自动化测试、外部依赖与生产交付边界

## 0. 本文要回答的问题

本文不回答“页面做了多少”，而回答以下五个问题：

1. 用户能否从入口一直完成到可验证结果。
2. 结果是否由服务端权威确认，而不是只保存在浏览器或设备。
3. 第三方、AI、渠道、KYC、支付或链上结果是否真实接入。
4. 失败、重试、撤销、回滚、申诉、审计是否存在。
5. 是否达到可封闭内测、可外部试点或可生产运营的标准。

## 1. 结论先行

### 1.1 当前产品所处阶段

Airvana 当前已经达到“高完整度移动端本地演示 + 单节点本地服务 MVP + 原生演示壳”的阶段，尚未达到“统一数据、真实外部服务、可生产运营”的阶段。

当前最重要的事实是：

- 移动端 `/` 已有完整产品外观、26 项功能入口和大量可操作本地状态。
- 首页已有 38 个可启动、可交互、可完成、可失败、可重玩的本地游戏，不再只是静态封面。
- `/workspace` 已有 Node.js + SQLite 权威状态机，覆盖钱包签名、Agent 任务、内容、Campaign、交付、归因事件、结算、举报、申诉和 Kill Switch 等能力。
- 完整自动化测试已通过 186/186；结构校验通过 29/29；`/`、`/workspace`、`/api/health` 当前均返回 HTTP 200。
- 网络/地区风控已完成前端演示闭环：正常、弱网、无网络、中国大陆、非金融模式、三类弹窗、状态条、高风险入口拦截、本地事件记录和恢复默认环境。
- iOS 与 Android 演示壳均存在，但演示壳不包含 Node.js/SQLite 后端，不能把“可安装”视为真实业务服务已经上线。

仍然没有完成的核心闭环是：

1. 移动端与本地服务仍是两套业务状态，缺统一 Data Adapter 和服务端 entitlement。
2. Campaign Contract 尚未成为贯穿创作、发布、归因、结算的独立版本化权威对象。
3. 素材、Artifact、外部渠道、KYC、真实 AI 媒体生成和链上/支付依赖仍未生产接入。
4. 玩家、KOL、品牌、平台运营之间的数据、权限、审批和证据尚未统一。
5. 生产基础设施、可观测性、安全、合规、商店发布和运营组织仍未闭环。

### 1.2 不应继续采用的判断方式

以下情况都不能再标记为“功能完成”：

- 有页面入口，但数据只在当前设备或 `localStorage`。
- 按钮可点击，但没有服务端状态变化。
- 本地 API 存在，但移动端没有接入。
- 显示“已发布、已结算、已 KYC”，但没有第三方或服务端证据。
- 产生了 CTA 点击，但没有商户服务端确认转化。
- 填写了 tx hash，但没有真实链上广播、确认和对账。
- 原生包装可安装，但后台、推送、深链、商店签名和生产 API 未接。

## 2. 统一成熟度与闭环标准

### 2.1 成熟度分级

| 等级 | 名称 | 判定标准 |
| --- | --- | --- |
| M0 | 需求/架构 | 只有说明、入口占位或架构标注 |
| M1 | UI 展示 | 页面与视觉存在，核心操作不能形成结果 |
| M2 | 本地演示闭环 | 当前设备可完成操作、失败和恢复，但结果不是权威业务结果 |
| M3 | 本地服务闭环 | Node/SQLite 等本地服务能权威执行业务状态机并产生审计证据 |
| M4 | 集成闭环 | 移动端、服务端与所需第三方在测试/预发布环境形成一条真实端到端链路 |
| M5 | 生产闭环 | 具备生产权限、监控、安全、合规、运营、回滚、对账和 SLA，可真实运营 |

一个模块可以同时呈现“移动端 M2、Workspace M3”。这表示能力存在但尚未统一，不得按更高等级对外表述。

### 2.2 真正闭环的统一公式

`入口 → 身份与权限 → 前置条件 → 核心操作 → 服务端权威状态 → 外部确认（如需要） → 通知与审计 → 失败/重试 → 暂停/撤销/回滚 → 数据保留/导出/删除`

对于 Agentic Playable，还必须满足：

`Campaign Brief → Campaign Contract → Playable/Version → Asset Manifest → 生成任务 → QA → 人工审核 → 发布清单 → Runtime 事件 → 归因证据 → 结算证据 → 复盘/复制`

### 2.3 高风险动作的额外门槛

预算、奖励、CTA 目的地、地区、合规声明、归因规则、结算、数据政策和 Kill Switch 必须保持锁定，由服务端权限和人工审批控制。外部服务不可用或证据不足时必须 Fail Closed。

## 4. 当前最关键的 12 个闭环阻塞

### B01. 移动端与 Workspace 状态分裂

- 移动端大量功能依赖本地状态，Workspace 使用本地 API 和 SQLite。
- 相同概念可能存在两套状态：角色、Campaign、作品、审核、归因、结算、治理。
- 这是当前最大的系统性风险；继续增加页面会加重漂移。

完成标准：建立统一 Data Adapter，页面只调用同一套领域接口，可切换 mock/local/staging；真实权限和结果始终以服务端为准。

### B02. 账号、角色、KYC 与 entitlement 未统一

- 钱包签名和本地会话存在，邮箱和 Google 仍是本地适配器。
- 创作者申请、KYC、节点、超级节点、商业权限仍是分离演示。
- 视角切换不会提升权限是正确边界，但尚缺统一服务端判定。

推荐公式：

`commercial_entitlement = account_active AND creator_approved AND kyc_valid AND region_allowed`

完成标准：补充材料、拒绝原因、重提、申诉、到期复核、暂停/恢复、设备会话和权限联动全部可审计。

### B03. Campaign Contract 还不是全链路权威对象

- 当前 Campaign 表单和本地服务有 Contract 字段，但缺独立、不可混淆、可版本化、可签署的 Contract 对象。
- 锁定字段的变更申请、审批、版本生效时间和旧版本证据未贯穿构建、事件、发布、结算。

完成标准：每次构建、发布、事件和结算都绑定 `campaign_id + contract_version + playable_id + version_id`；锁定字段变更生成新版本并重新审批。

### B04. Asset Manifest 与素材证据未生产化

- 当前本地素材库、用途、排序、授权提示和快照已可演示。
- 缺对象存储、CDN、校验和、病毒/内容扫描、转码、来源与授权凭证、到期/撤销和删除策略。

完成标准：发布构建只能引用通过检查的不可变素材快照；授权撤销可追溯影响范围并触发下架/替换流程。

### B05. 创作任务、审核、构建和移动端发布未统一

- 服务端已有 Agent Task、Worker、审核、Artifact、版本和发布状态机。
- 移动端创作器仍主要完成本地演示，没有消费同一任务 ID、进度、失败原因、重试、取消和人工审核结果。

完成标准：移动端发起真实本地/预发布任务，能看到服务端步骤证据；审核通过后生成 Release Manifest，发布、暂停、回滚由服务端执行。

### B06. Artifact 托管与 Runtime 事件证据未统一

- 本地游戏可玩，服务端也有 Artifact 和有序 Runtime Proof。
- 首页没有统一加载服务端发布的 Artifact 版本；本地游戏事件与服务端证据仍分离。

完成标准：远程/本地 Artifact 使用同一运行时协议；事件包含稳定 ID、顺序号、时间、会话、KOL 链接和隐私状态；重复、乱序和伪造事件被拒绝。

### B07. 外部发布连接器尚未接入

- Telegram、Facebook、X、Discord 当前是页面/流程方案。
- 缺 OAuth/Bot/API、Token Vault、目标选择、人审确认、回调、重试、撤权和审计。

完成标准：先只选一个试点渠道；只有审核通过且 Contract 允许的版本可发布；外部回调确认前不得显示“发布成功”。

### B08. 归因尚未覆盖真实转化

- 服务端已有 impression、playable_start、playable_complete 和基础 attribution touch。
- 缺 KOL 专属链接、Click ID、CTA view/click、服务端商户转化、幂等、去重、窗口、反作弊、隐私同意、撤销/退款和跨设备处理。

完成标准：第三方或商户服务端确认的注册/KYC/购买才可标记为已验证转化；客户端点击只能算意图事件。

### B09. 三套账本与真实结算未生产化

必须继续分离：

1. 玩家 AIP：不可提现的站内行为积分/权益。
2. AIT：获批 Campaign Contract 下的中心化权益与收益凭证，不可自由转让或交易。
3. KOL 商业结算：基于已批准交付和归因证据的独立商业应付与付款记录。

本地 V1 已具备 AIP/AIT 批次、期限、冻结、撤销、申诉、Contract 预算/成功事件校验，以及与 AIT 分离的权益申领和付款/回执记录。旧通用提现与旧 AIT 发放入口固定返回 `410`。生产仍缺第三方 KYC、权威归因事件、真实支付/托管、财务对账、税务、退款和监控基础设施。

完成标准：任何余额变化均有不可分离的业务事件、审批、账本分录、外部回执和审计；失败可冲正，争议可冻结。

### B10. AI 分身的真实服务和授权未闭环

- 人设、场景、语言、知识、版本、暂停、回滚和动作演示已较完整。
- 当前视频样例和动作素材不是实时分身生成；未接模型训练、实时语音/视频、声音/肖像授权、知识隔离服务和外部渠道自动运营。

完成标准：授权范围、模型版本、知识来源、场景隔离、输出审核、停用、删除和生成日志可审计；不得把预生成样例描述为实时数字分身。

### B11. 治理、客服、未成年人和法律落地未闭环

- 本地服务已有举报、申诉、风险案件和 Kill Switch；移动端仍未统一接线。
- 客服工单、SLA、升级、附件、通知和运营工作台不完整。
- 未成年人模式明确未启用，缺年龄、监护、内容、时长、社交、钱包和地区策略。
- 用户协议和隐私政策仍缺运营主体、注册地址、正式邮箱、首发地区、适用法律、第三方/SDK 清单和法律顾问复核。

完成标准：策略版本、权限、案件 SLA、证据保留、用户通知、申诉、恢复和事故响应进入服务端；正式法律文本与真实数据流、供应商和地区一致。

### B12. 生产基础设施与运营能力未闭环

仍缺：

- 托管 PostgreSQL 和迁移/回滚方案。
- 分布式队列、多实例 lease、死信与幂等。
- 对象存储/CDN、密钥管理和凭证轮换。
- 日志、指标、追踪、崩溃报告、告警和值班。
- CI/CD、灰度、回滚、备份恢复演练、容量和灾难恢复。
- 安全扫描、依赖治理、渗透测试和生产权限分离。
- App Store/Google Play 正式包名、签名、隐私清单、审核素材和版本发布流程。

完成标准：不是“可以部署”，而是能够检测故障、限制影响、回滚、恢复和复盘。

## 5. 五条端到端主链审计

### 5.1 用户与资格链

目标链路：

`启动 → 登录 → 会话 → 玩家 → 创作者申请 → KYC → 平台审核 → entitlement → 暂停/恢复 → 数据导出/注销`

当前结论：移动端 M2，本地钱包/会话/账号数据 M3，第三方认证和统一权限未达 M4。

主要断点：真实邮件/OAuth、账号合并、找回/MFA、KYC、到期复核、商业权限、外部授权撤销和全数据生命周期。

### 5.2 KOL 创作与发布链

目标链路：

`机会/Brief → Contract → 素材 → 生成 → QA → 审核 → 站内发布 → 外部分发 → 版本/暂停/回滚`

当前结论：移动端创作演示 M2，Workspace 本地任务/审核/发布 M3，二者未统一，外部服务未达 M4。

主要断点：Contract 版本、真实素材仓、任务接线、Release Manifest、远程 Artifact、渠道连接器和发布回调。

### 5.3 玩家体验与社交留存链

目标链路：

`发现 → 体验 → 完成/失败/重玩 → 点赞/评论/收藏/分享 → 关注 → 消息 → 重访 → 举报/屏蔽`

当前结论：游戏本地体验 M2 较强，社交关系和消息主要 M2，跨设备权威数据、实时服务和推送未达 M3/M4。

主要断点：服务端推荐/搜索、关系图、评论、收藏、私信、未读同步、推送、屏蔽、内容安全和归因事件统一。

### 5.4 Campaign、归因与结算链

目标链路：

`品牌组织 → Campaign → 邀请/申请 → Contract → 交付 → 审批 → 运行事件 → 真实转化 → 对账 → 结算 → 争议`

当前结论：Workspace 有一条可测试的本地 M3 状态机，移动端是独立 M2 演示，真实渠道/转化/支付未达 M4。

主要断点：品牌权限、Contract 签署、KOL 链接、商户转化、隐私、反作弊、三账本、支付/链上和争议。

### 5.5 治理、运维与数据生命周期链

目标链路：

`风险/举报 → 受理 → 分级 → 暂停/下架/冻结 → 人工裁决 → 申诉 → 恢复/维持 → 通知 → 审计/复盘`

当前结论：Workspace 本地治理 M3，移动端接线和生产运营流程未达 M4/M5。

主要断点：RBAC、策略发布、告警、案件 SLA、运营工作台、证据保留、事故响应、备份恢复和法务协作。

## 8. 推荐推进顺序（按验收门，而不是继续堆页面）

### 阶段 A：建立“状态可信”底座

范围：F01、F02、F03、F09、F10。

验收门：

- 功能中心不再只显示“前端已展示/服务端待接”，而显示 UI、Demo、Local API、Integrated、External、Production 六层证据。
- 玩家/KOL 切换只切视图，服务端 entitlement 决定动作。
- 所有高风险动作有统一审计事件和 Fail Closed 结果。

### 阶段 B：打通一条可信的本地/预发布主链

推荐主链：

`创作者资格 → Brief → Contract → Asset → Agent Task → QA → 人审 → 站内发布 → Runtime Events → 归因报告`

范围：F04、F05、F06、F07，并把 R02、R10–R17、R20、R23、R25 接到同一服务。

验收门：移动端与 Workspace 对同一个对象显示一致状态；刷新、换设备、失败、重试、暂停和回滚后仍一致。

### 阶段 C：完成一个真实商业试点

建议只选择：

- 一个品牌/买方。
- 一种 Playable 模板或一组受控游戏机制。
- 一个外部发布渠道。
- 一个主要转化事件。
- 一个 KOL 商业结算指标。
- 一个目标地区和合规方案。

验收门：从签署 Contract 到渠道发布、商户服务端转化、对账、审批和结算形成一条真实证据链，并能暂停、回滚和申诉。

### 阶段 D：生产化与应用商店交付

范围：F08、F11、F12，生产基础设施、正式法律文本、商店材料、设备矩阵、安全与运营值班。

验收门：完成灰度发布和回滚演练、备份恢复演练、权限审计、安全评审、隐私核对和真实设备验收后，才进入公开运营。

### 暂不建议同时启动

- 四个以上外部渠道并行接入。
- 增长网络经济节点或智能合约。
- 多链、多 Token 或复杂 DeFi 能力。
- 全实时 3D/视频数字分身。
- Agent 自动改预算、结算、地区、合规或发布策略。
- 在没有统一事件和 Contract 前做复杂自动优化。

## 9. 需要产品确认的 12 个决策

| # | 决策 | 推荐方案 | 不确认的影响 |
| --- | --- | --- | --- |
| D01 | 下一阶段目标 | 先做“可信预发布主链”，不继续零散扩页面 | 双状态继续扩大，无法判断完成度 |
| D02 | 第一优先用户 | KOL 创作者为主，玩家体验为辅；品牌/运营使用 Workspace | 四端同时建设导致主链失焦 |
| D03 | 商业权限 | 账号正常 + 创作者通过 + KYC 有效 + 地区允许 | 本地视角可能被误当成真实权限 |
| D04 | 玩家作品商业化 | 复制为新的 KOL 商业版本并重新走 Contract | 原地升级会混淆数据、授权和结算 |
| D05 | Contract 模型 | 独立版本化权威对象，锁定字段变更必须重审 | 归因和结算无法证明使用了哪版规则 |
| D06 | 首个真实渠道 | 只接 1 个渠道试点，再扩展 | 同时接 4 个渠道会放大凭证和回调复杂度 |
| D07 | 首个真实转化 | 选 1 个服务端可确认事件作为结算依据 | 点击/客户端事件不能支持可靠结算 |
| D08 | 账本边界 | AIP、AIT、KOL 商业结算保持三套独立账本 | 容易产生资产、会计和合规混淆 |
| D09 | AI 分身范围 | 第一阶段做授权、记忆、版本与受控输出；实时视频后置 | 实时媒体会抢占主链和合规资源 |
| D10 | 增长网络范围 | 先做协作关系与贡献证据，经济节点后置 | 过早经济化会放大身份、结算和监管风险 |
| D11 | 首发地区 | 先确定一个目标地区，再确定 KYC、法律、数据和商店要求 | 协议、供应商、跨境和未成年人规则无法定稿 |
| D12 | 发布目标 | 先封闭内测/外部试点，再进入商店生产版 | 直接商店化会同时暴露基础设施与合规缺口 |

建议一次性确认 D01–D08；D09–D12 可在进入外部试点前确认。

## 10. 下一阶段建议验收清单

产品确认后，第一批开发不以“新增页面数”为验收，而以下列证据为准：

1. 同一用户在移动端和 Workspace 看到同一账号、角色、权限和会话状态。
2. 同一 Campaign Contract 有版本、锁定字段、审批人、生效时间和变更记录。
3. 同一 Playable 的素材、任务、构建、审核、发布和 Runtime 事件可通过稳定 ID 串联。
4. 页面刷新、换设备或重启后，服务端权威状态不丢失。
5. 弱网/离线/第三方失败不会制造假成功；恢复后可重试或人工接管。
6. 未经审批不能发布、外发、结算或执行高风险 Web3 动作。
7. 客户端事件不直接生成商业结算；必须等待服务端转化和对账证据。
8. 每个状态变化都有主体、时间、对象、前后值、理由和结果。
9. 每个 P0 主链都有成功、拒绝、失败、重试、撤销、暂停和回滚测试。
10. 功能中心可展示每项能力的最新证据、测试和外部依赖，而不是只显示概括性标签。

## 12. 最终建议

Airvana 现在不缺“更多页面”，缺的是把已经存在的移动端产品、Workspace 状态机、38 个完整本地游戏和风控边界收敛为一条可信主链。

建议确认后只启动一件事：

> 以 KOL 创作者为第一优先用户，使用统一 Data Adapter 和服务端 entitlement，打通“资格 → Campaign Contract → 素材 → 生成 → 审核 → 站内发布 → Runtime 事件 → 归因证据”的同一对象、同一状态、同一审计链。

完成这条链后，再选择一个外部渠道、一个真实转化和一个结算指标做试点；在此之前不扩大经济节点、多渠道、实时数字分身或复杂自动优化范围。
