# Airvana UI 与完整功能闭环结构性需求文档

> 版本：v2.0
> 日期：2026-08-12
> 范围：`airvana-v5-fullstack` 移动端、品牌/平台工作台、本地服务端与 Android 演示壳
> 文档状态：项目审计与下一阶段需求基线；不是生产发布批准
> 核心定位：让每一个 KOL 创作并运营属于自己的 Agentic Playable。KOL 是创作者、所有者和运营者；Agentic Playable 是可持续运营的营销智能体。

## 1. 文档目标

本文件合并并升级已有的“26 项结构化需求清单”和“未完成功能闭环审计”，解决四个问题：

1. UI 已经具备较完整的产品形态，但组件、主题、信息密度、状态透明度和性能仍需要系统收敛。
2. 本地服务端已经具备多条真实业务状态机，但移动端大量功能仍使用独立的本地演示状态。
3. “页面已展示”“本地服务已验证”“第三方已接入”“生产可运营”必须使用不同状态，不得统一显示为“已闭环”。
4. 下一阶段需要从零散页面优化切换为可追踪、可验收、可发布、可回滚的端到端建设。

本文件回答两类需求：

- **UI 层**：视觉系统、信息架构、交互状态、移动适配、无障碍、性能和视觉回归。
- **完整功能闭环**：从 Brief、Contract、生成、审核、发布到互动、归因、交付、结算、治理和复盘的权威状态链路。

## 2. 结论先行

### 2.1 当前项目定性

当前项目应定义为：

**可运行、可安装、具有较完整本地后端状态机的受控全栈 MVP；移动端仍以本地演示为主，不是可公开运营的生产 APP。**

已经确认的能力：

- 移动端具备首页、发现、增长网络、消息、我的五大入口，以及中心创作入口。
- 本地服务端具备认证、Agent 任务、内容审核、版本、Artifact、运行证明、Campaign、交付、结算、治理和数据权利等能力。
- 品牌与平台工作台能够访问本地 API。
- Android 演示 APK 可安装，内嵌当前前端资源。
- 全量自动化测试在允许绑定本地端口的环境中为 **140/140 通过**；结构验证为 **29/29 通过**。

尚未完成的核心：

- 移动端只调用约 11 类 API 路径，而后端已有约 67 类路由模式；前后端能力没有统一接线。
- Campaign Contract 仍需升级为独立、版本化、可签署、可追踪变更的生产对象。
- Asset Manifest 仍以浏览器本地存储为主，没有对象存储、授权证据、扫描和 CDN 生命周期。
- 邮箱/Google 登录、KYC、外部发布连接器、真实媒体生成、外部转化确认和链上广播仍依赖第三方。
- 单机 SQLite、内存式 Worker 轮询、本地文件 Artifact 和本地密钥配置不满足生产扩展要求。

### 2.2 下一阶段唯一主目标

下一阶段不应继续以“增加页面数量”为目标，而应完成以下闭环：

`Campaign Brief → Campaign Contract → 资产与授权 → Agent 生成任务 → 约束与审核 → 版本化 Artifact → 受控发布 → KOL 链接与运行事件 → 归因证据 → 交付审批 → 商业结算 → 复盘与新版本`

## 3. 证据状态定义

所有功能、页面和里程碑统一使用以下状态：

| 状态 | 含义 | 是否可作为生产完成证据 |
| --- | --- | --- |
| UI | 有入口和主要界面 | 否 |
| DEMO | 当前设备内可完成本地演示 | 否 |
| LOCAL | 本地服务端有权威状态并通过自动化测试 | 仅用于本地验收 |
| INTEGRATED | 移动端/工作台已经接入服务端，并覆盖失败和恢复 | 可用于受控测试 |
| EXTERNAL | 第三方服务、凭证、回调和撤销已验证 | 取决于环境与审批 |
| PROD | 生产基础设施、监控、备份、发布和运营责任人已完成 | 是 |
| BLOCKED | 缺产品决策、合规审批、外部依赖或关键证据 | 否 |

禁止使用“26/26 已闭环”表达 UI 覆盖率。建议并列展示：

- 页面覆盖率；
- 本地闭环率；
- 服务接线率；
- 外部依赖完成率；
- 生产就绪率。

## 5. UI 层结构性需求

### 5.1 UI 总体原则

1. 页面覆盖不等于功能完成；状态必须准确。
2. 视觉尺寸、触控区域和无障碍语义分别治理。
3. 暗黑和浅色必须由语义 Token 驱动，禁止新增硬编码主题色。
4. 核心路径采用渐进披露，首屏只展示当前决策所需信息。
5. 所有列表、表单和异步动作必须包含加载、空、错误、离线、无权限和恢复状态。
6. 用户看到的状态必须标明来源：本机、服务端、第三方、链上或待确认。

### 5.3 关键页面详细要求

#### UI-006：首页 Feed

当前问题：

- 23 个作品同时存在于 DOM 和可访问树中。
- 非当前作品的按钮仍可被自动化和辅助技术发现。
- 多封面和媒体会增加解析、内存和 APK 资源负担。

要求：

- 仅渲染 `current - 1 / current / current + 1` 三个窗口，或使用等价虚拟化方案。
- 非活动项必须 `inert`、`aria-hidden=true`，不可获得焦点。
- 作品切换后保持点赞、收藏、关注和进度状态一致。
- 封面失败时展示品牌安全的本地占位，不出现空白或布局跳变。
- 首次进入只预加载当前封面，相邻封面低优先级预取。

验收：

- 当前 Feed 的可交互控件数量不随作品总数线性增长。
- 50 个作品时内存和首次交互仍符合性能预算。
- 连续快速滑动、刷新、切后台和返回均不会丢失当前作品状态。

#### UI-007：创作器

建议结构：

`Brief → 目标与受众 → 素材与授权 → 能力/模板 → 方案预览 → Contract 核对 → 生成任务`

要求：

- 快速模式首屏只保留创意输入、目标完成度、素材状态和一个主操作。
- 能力编排默认折叠为推荐摘要；用户主动展开后再展示分类和完整能力列表。
- 深度模式明确显示 Contract 锁定字段、可编辑字段和 Agentic 字段。
- 背景层不得穿透到影响输入和按钮对比度。
- 每一步显示“为什么需要”“当前来源”“是否保存”“是否影响 Contract 版本”。
- 生成、取消、失败、重试、恢复和离开页面必须由同一任务状态机控制。

验收：

- 新用户不阅读帮助也能在 3 个主决策内发起第一个本地预览。
- 不填写 Brief 必填项时不能进入生产生成。
- 修改锁定字段必须创建 Contract 变更，不得静默覆盖。

#### UI-001：功能中心

要求：

- 顶部改为“26 项功能已收录”，不要显示“26/26 已闭环”。
- 为每项功能展示：UI、DEMO、LOCAL、INTEGRATED、EXTERNAL、PROD 六层进度。
- 进度条只汇总当前选择的层级。
- 每个功能可展开查看证据、测试、依赖、负责人、阻塞和下一动作。
- 玩家/KOL 视角只过滤动作，不修改账号权限。

验收：

- R15 外部连接器不能与 R05 本地体验显示相同完成状态。
- 任何状态升级必须绑定测试、API、第三方回调或发布证据。

#### UI-005：全局状态组件

所有异步页面至少覆盖：

- 首次加载；
- 局部刷新；
- 空数据；
- 权限不足；
- 待审核；
- 服务不可用；
- 离线；
- 第三方授权过期；
- 操作冲突；
- 重试后恢复。

组件文案必须回答：发生了什么、是否已保存、下一步是什么、是否会产生真实外部动作。

## 6. 完整功能闭环需求

### 6.1 完成定义

任一功能只有具备以下链路，才可标记为闭环完成：

`入口 → 权限/前置条件 → 核心操作 → 服务端权威状态 → 结果通知与审计 → 失败/重试 → 暂停/撤销/回滚 → 数据导出或删除`

### 6.2 主业务链路现状与目标

| 阶段 | 当前能力 | 核心断点 | 目标需求 |
| --- | --- | --- | --- |
| Brief | 移动端目标、受众、素材和创意输入已有 | 与服务端 Campaign Brief 不是同一对象 | 建立版本化 Brief，记录事实、假设、待录入项和来源 |
| Contract | 服务端 Campaign 有 Brief、预算、CTA、地区和可优化字段 | 缺独立 Contract ID、版本、签署、变更单和字段级锁定 | Contract 成为生成、审核、发布、归因和结算唯一生产源 |
| Asset Manifest | 移动端支持本地添加、用途、焦点和授权状态 | IndexedDB 仅当前设备；无真实授权证据和扫描 | 对象存储、checksum、来源、授权、扫描、到期和撤销闭环 |
| Agent 任务 | 服务端 Task、Worker、AI Adapter 和步骤证据已通过测试 | 移动端生成流程主要为本地状态 | 移动端通过 API 创建任务、轮询/订阅状态、取消、重试和恢复 |
| 约束与审核 | 本地策略和人工审核门禁已存在 | Contract 约束未形成字段级统一校验服务 | Schema → Policy → Permission → Human Review 顺序固定并可审计 |
| 版本/Artifact | 服务端内容版本、恢复和 Artifact 构建已存在 | 移动端版本与服务端版本未统一 | 每个版本绑定 Contract、Manifest、生成任务、验证报告和 checksum |
| 发布 | 服务端站内发布、计划发布和归档已存在 | 移动端仍有“发布到本地演示”独立链 | 站内发布由服务端权威状态驱动，审批通过后人工确认 |
| 外部分发 | 前端展示连接器方案 | 无 OAuth、目标确认、回调、重试和撤销 | 先接一个试点连接器，支持授权、发布确认、失败和撤销 |
| 运行事件 | 服务端按顺序验证 start/step/complete 并防直接领奖 | 移动端 Feed 与 Artifact 事件未统一 | 统一事件 SDK、幂等 event_id、session、consent 和版本字段 |
| 归因 | 服务端记录 impression/start/complete | 缺 click_id、CTA、外部 confirmed conversion、去重和窗口 | KOL 专属链接、优先级、归因窗口、防刷、外部确认和证据状态 |
| 交付 | Campaign Deliverable 审核已通过测试 | 移动端未显示权威交付对象和审阅历史 | 提交、整改、重提、批准、拒绝和证据快照全部可追踪 |
| 结算 | 本地 AIT Settlement 和钱包提现状态机已通过测试 | 真实 KYC、支付/托管、链广播和财务对账未接 | 玩家权益、KOL 结算、品牌预算三账分离；人工与平台双审批 |
| 运营优化 | 本地事件、版本和 Agent Memory 已有 | 没有受控实验、诊断报告和自动优化门禁 | 仅在 Contract allowlist 内提出 patch，经评估、审批、灰度和回滚 |

### 6.3 P0 可验收主链路

P0 必须用同一批真实本地对象完成以下流程：

1. 品牌创建 Campaign Brief。
2. 系统生成 `contract_id + contract_version`，锁定地区、CTA、奖励、成功事件、归因和结算字段。
3. 平台审核品牌组织和 Contract。
4. KOL 被邀请或申请，并由服务端确认 eligibility。
5. KOL 接受 Contract 后创建 Agentic Playable。
6. 素材进入 Asset Manifest，未授权素材阻止提交。
7. 移动端创建服务端 Agent Task，显示步骤、失败、重试和取消。
8. 生成结果进入人工审核，不允许生成后直接发布。
9. 审核通过后构建版本化 Artifact，并生成 checksum 和验证报告。
10. KOL 人工确认站内发布，平台保留暂停和 Kill Switch。
11. 系统生成 `campaign_id + playable_id + version + kol_id + link_id` 专属链接。
12. 用户完成曝光、开始、步骤和完成事件；重复和乱序事件被拒绝或去重。
13. 外部成功事件仅由批准的品牌系统确认，不把 CTA 点击当成转化。
14. KOL 提交 Deliverable，品牌审批，平台复核结算。
15. 结算生成独立账本记录；失败、取消、冻结和申诉可追踪。
16. 运营者查看漏斗与证据，创建允许字段的新版本，原版本可回滚。

验收要求：

- 全链路使用同一组稳定 ID 和版本号。
- 每一步有角色权限、时间、输入、结果、失败原因和审计记录。
- 任何页面刷新或跨端打开后状态一致。
- 敏感动作具备幂等键，重复提交不产生重复对象、事件或结算。
- Kill Switch 能阻止新任务/发布，并保留历史证据。

## 7. 支撑业务闭环

### 7.1 账号与角色资格

链路：

`注册/登录 → 会话 → 玩家 → 申请创作者 → KYC → 平台审核 → KOL entitlement → 暂停/过期/申诉/降级`

要求：

- `view_role` 与真实 `entitlement` 分离。
- 移动端接入服务端会话、设备管理、导出和删除请求。
- 邮箱验证码、Google OAuth 和钱包签名使用同一账号合并策略。
- KYC 原始证件直接交由批准的第三方；Airvana 仅保存状态、引用和必要时间。
- KYC 过期后作品和证据只读保留，禁止新建、发布和结算。

### 7.2 素材、版权与媒体

要求：

- 每个素材记录 `asset_id`、checksum、来源、所有者、用途、授权范围、到期时间和扫描结果。
- 未授权、过期或被撤销素材立即阻止新版本发布。
- 已发布版本保留不可变素材快照，不因素材库替换而静默变化。
- 图片生成多尺寸 WebP/AVIF；视频使用流式或按需下载，不内嵌全部样片到基础 APK。

### 7.3 消息、关系与通知

要求：

- 通知、互动和私信由服务端统一未读数，不由页面分别维护。
- 支持发送中、发送失败、重试、撤回、屏蔽、举报和会话归档。
- Campaign、审核、发布、连接器、归因和结算消息可深链到对应对象。
- 推送只作为提醒，权威状态仍从服务端加载。

### 7.4 AI 分身

要求：

- 平台个人资料与 AI 分身身份继续分离。
- `scene_id + campaign_id + contract_version` 隔离知识、话术和权限。
- 声音、肖像、知识和渠道授权分别记录，可撤销、可到期。
- 外部渠道默认只生成回复建议，由本人确认后发送。
- 始终显示 AI 标识，支持人工接管、暂停、版本回滚和审计。

### 7.5 AIP、AIT 与商业结算

三类账本必须分离：

1. 玩家/用户 AIP 站内行为权益；
2. 活动权益 AIT 记录；
3. KOL Campaign 商业结算与品牌预算。

要求：

- AIP 不可提现、不可承诺固定价值或兑换投资回报。
- KOL 结算必须绑定 Contract、Deliverable、归因证据、KYC 和审批链。
- 钱包绑定、提现、冻结、取消、失败和链上确认使用服务端状态机。
- 真实链上完成必须保存交易哈希并由批准的链/托管服务确认。

### 7.6 增长网络

第一阶段建议定义为协作网络，而非经济节点：

- 玩家可接受邀请并查看个人贡献；
- KOL 可创建节点、邀请、管理席位和暂停；
- 五个席位拥有独立成员、状态和贡献证据；
- 信用分、Power 和贡献由服务端计算，不直接等同收益；
- 智能合约、经济分配和超级节点进入后续独立审批。

### 7.7 治理与数据生命周期

要求：

- 举报、受理、处理、下架、申诉、恢复形成状态机。
- 平台终审、全局 Kill Switch、KYC 确认和结算确认不得下放给 KOL。
- 数据导出、删除申请、冷静期、撤销、外部授权查看和撤销均可追踪。
- 删除请求不得抹除依法或合同要求保留的审计和结算证据；需要单独保留策略。

## 8. 数据与系统架构需求

### 8.1 统一移动端数据层（P0）

建立领域适配器：

```text
AuthRepository
ProfileRepository
PlayableRepository
TaskRepository
CampaignRepository
AttributionRepository
SettlementRepository
MessageRepository
GovernanceRepository
```

要求：

- 页面不得直接判断 `frontendDemoMode` 决定业务结果。
- 数据源支持 `mock / local-api / staging / production`，由环境配置注入。
- 每个返回对象包含 `source`、`server_confirmed`、`updated_at` 和 `version`。
- 写操作使用乐观更新时必须支持回滚和冲突提示。

### 8.2 状态机与权限服务（P0）

- 状态和允许动作由服务端返回，不在多个页面重复推导。
- 每个动作检查角色、entitlement、对象所有权、Contract 版本和对象状态。
- 玩家/KOL 视角切换不得生成新权限。
- 预算、奖励、地区、CTA、归因、结算、合规、数据策略和 Kill Switch 默认锁定。

### 8.3 Contract 与版本服务（P0）

核心字段：

```text
contract_id
campaign_id
version
status
owners
objective
audience
channels
brand
gameplay
cta
reward
compliance
data_policy
measurement
attribution
commercial
locked_fields
editable_fields
agentic_fields
approval
release
```

要求：

- 任何锁定字段变化创建新 Contract 版本和变更记录。
- 生成任务、Artifact、发布、事件、Deliverable 和 Settlement 均引用同一 Contract 版本。
- 被替换版本只读保留，不覆盖历史证据。

### 8.4 统一事件与归因（P0）

事件最小单元：

`谁 + 在哪个会话/版本 + 看到了什么 Agent 决策 + 做了什么 + 产生了什么结果`

事件必须包含：

```text
event_id, event_name, event_time
campaign_id, contract_version
playable_id, playable_config_version, build_id, creative_id
channel_id, kol_id, link_id, session_id
user_or_anon_id, consent_state
region, locale, device_class, experiment_id
sequence, properties
```

要求：

- 事件幂等、顺序可校验、原始事件不可覆盖。
- CTA 点击与 confirmed conversion 分开。
- 归因定义包含 numerator、denominator、窗口、优先级、去重和排除规则。
- consent 被拒绝时不采集被禁止字段。

### 8.5 生产基础设施（P1）

- PostgreSQL 与正式 migration；
- 分布式任务队列、租约和死信处理；
- 对象存储、CDN、媒体转码和签名 URL；
- 生产密钥管理与环境隔离；
- 集中日志、指标、Trace、告警和审计检索；
- 数据库和对象存储备份、恢复演练；
- 容器化、健康检查、灰度发布和一键回滚；
- 容量、并发、弱网和故障注入测试。

## 9. 非功能需求

### 9.1 安全与隐私

- 不收集私钥、助记词、密码或原始 KYC 文档。
- 会话 Cookie 保持 HttpOnly、SameSite 和生产 Secure。
- 所有外部回调验证签名、时间窗、防重放和幂等。
- 用户数据、品牌数据、Campaign 数据和模型上下文按租户与角色隔离。
- 生产日志禁止记录 Token、签名原文、敏感身份资料和完整钱包凭证。

### 9.2 可用性与可靠性

- 外部 AI、KYC、连接器、链或分析服务失败时失败关闭。
- 失败必须提供重试、撤销、回退或人工接管，不可伪造成功。
- 后台任务具备超时、重试上限、取消、租约、死信和人工重放。
- 关键动作使用幂等键，重复请求不重复扣款、发布或结算。

### 9.3 可观测性

每个关键请求和任务绑定：

`trace_id + user_id + campaign_id + contract_version + playable_id + version + task_id`

至少监控：

- 登录、任务、审核、构建、发布成功率；
- 事件丢失、重复、乱序和延迟；
- 外部连接器、KYC、AI 和链服务错误率；
- Campaign 预算、结算和账本不一致；
- Kill Switch、下架、申诉和高风险操作；
- Web 首屏、媒体加载、崩溃和 Android WebView 错误。

## 11. 验收门禁

### 11.1 任一功能的 Definition of Done

- 有服务端权威对象和稳定 ID。
- 有明确角色和动作权限。
- 有成功、失败、加载、空、离线、冲突和过期状态。
- 有幂等、审计、通知、撤销或回滚。
- 有数据来源和确认级别。
- 有自动化测试和代表性移动端视觉证据。
- 不绕过 Contract、审核、风控、发布和结算门禁。
- 文档、API、UI 和实际状态一致。

### 11.2 发布门禁

- Contract/Config/Artifact 校验通过；
- 资产授权和到期检查通过；
- 内容、品牌、数据、隐私、安全和合规审批完成；
- 360/390/430、Android WebView 和桌面工作台通过；
- 事件、归因、去重、同意和失败路径通过；
- 发布 Manifest、上一稳定版本、回滚目标和 Kill Switch 负责人已记录；
- 监控窗口、阈值和告警责任人已确认。

## 12. 产品待确认决策

以下决策会影响实施范围，进入 P0 实施前需要确认：

1. 第一版目标是内部演示 APK、封闭内测，还是公开商店版本。
2. 第一优先角色是 KOL，还是需要同时完成品牌和玩家主路径。
3. P0 是否确认移动端默认连接本地 API，失败后只允许显式进入 DEMO，不自动伪装回退。
4. Campaign Contract 是否独立于 Campaign，采用版本和签署记录。
5. 第一版真实外部连接器选择 Telegram、X、Discord 或其他渠道。
6. 第一版 confirmed conversion 由哪个品牌系统回传。
7. KYC 服务商、地区、最低年龄和数据保留策略。
8. AIP 是否永久保持不可提现站内权益；AIT 与 KOL 商业结算是否继续严格分账。
9. 增长网络第一版是否只做协作关系，暂缓经济节点和智能合约。
10. 第一版语言范围和无障碍目标。
