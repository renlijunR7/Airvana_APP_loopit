# Airvana 全项目结构化需求清单

> 版本：v1.0
> 更新日期：2026-08-09
> 当前阶段：前端功能展示优先，后端与第三方能力按边界规划
> 目标：明确“已经能演示”“前端仍需补齐”“本地服务已有但未接线”“依赖外部系统”之间的差异，作为后续逐项开发和验收的唯一清单。

## 1. 产品基线

Airvana 的核心对象是 **Agentic Playable**。KOL 是 Agentic Playable 的创作者、所有者和运营者，不将 KOL 本人描述成 Agent。

标准生产链路：

`Campaign Brief → Campaign Contract → 创作与资产 → 审核 → 发布 → 互动与归因 → 结算与复盘`

当前阶段允许使用本地演示数据完成前端闭环，但必须满足以下边界：

- 演示数据必须明确标识为“演示”或“本地状态”。
- 不得把本地状态描述成真实 KYC、链上结算、提现、节点或超级节点权限。
- 不得在未接入外部服务时伪造 Telegram、Facebook、X、Discord 等渠道发布成功。
- 审核、发布、费用、结算、权限与 Kill Switch 不能由普通创作者在前端自行绕过。
- Campaign 的生产输入必须来自结构化 Brief 和 Contract，不以零散聊天内容替代。

## 2. 审计结论

项目内现有功能地图共 26 项，全部已有页面入口、交互雏形或本地服务基础。其中 18 项在代码中标记为“前端已展示”，但这只表示可以进入和演示，不等同于产品闭环或上线完成。

当前真正的断点有四层：

1. **移动端数据接线**：移动端固定处于 `frontendDemoMode = true`，大量页面没有接入已经存在的本地 API。
2. **前端完整状态**：部分页面只有成功路径，缺少加载、空、失败、离线、无权限、审核中、过期、撤销等状态。
3. **外部能力**：KYC、社交渠道连接、真实 AI、链上钱包、消息推送等依赖第三方或后端。
4. **生产基础设施**：生产数据库、队列、对象存储、密钥管理、监控、备份和发布治理尚未完成。

### 2.1 状态定义

| 标记 | 含义 |
| --- | --- |
| F1 | 前端已有入口或主要 UI，但仍需补齐状态或交互 |
| F2 | 前端本地演示闭环基本完成，可用于产品展示 |
| S | 本地服务端已有能力，但移动端尚未接入 |
| X | 依赖第三方服务、真实凭证或外部审核 |
| P | 依赖生产级基础设施或运营流程 |

## 5. 推荐推进顺序

### 阶段 0：建立可信的前端底座

- FE-01 统一数据适配层。
- FE-02 全局状态组件。
- FE-03 功能状态注册表。
- FE-04 跨页面本地数据一致性。
- FE-10 视觉与交互回归。

完成后，功能中心不再只展示“已展示/待接”，而能准确显示每项完成度和依赖。

### 阶段 1：打通用户核心体验

- R01 启动页。
- R05 Agentic Playable 体验。
- R06 发现。
- R07 消息。
- R08 搜索。
- R09 关注关系。
- R03/R04 AI 分身前端闭环。

### 阶段 2：打通创作者核心体验

- R10 创作者中心。
- R11 AI 创作流程。
- R12 素材与授权。
- R13 Remix/版本。
- R14 审核/发布。
- R16 Brief/Contract。

### 阶段 3：接入项目已有本地服务

- 解除页面对 `frontendDemoMode = true` 的直接依赖。
- 将登录、Agent、任务、内容版本、Campaign、审核、钱包、通知、治理逐项切到统一适配层。
- 保留 Mock 模式用于无服务演示和自动化测试。
- 该阶段只做已有 API 的前端接线，不扩展新的后端范围。

### 阶段 4：外部能力和生产化

- KYC 服务。
- AI 模型与媒体生成。
- Telegram/Facebook/X/Discord 发布连接器。
- 链上钱包与结算。
- 生产数据库、队列、对象存储、监控、备份与发布治理。

## 6. 全项目统一完成标准

任一功能只有同时满足以下条件，才可从“前端展示”升级为“前端闭环完成”：

1. 有明确入口、返回路径和刷新恢复策略。
2. 成功、加载、空、失败、离线、无权限等适用状态均有 UI。
3. 同一业务对象在不同页面的数据一致。
4. 危险操作有确认、撤销或清晰的不可逆提示。
5. 演示状态、服务端状态和第三方真实结果不混淆。
6. 不允许绕过 Contract、审核、权限、风控和发布门禁。
7. 核心流程具备自动化行为测试和移动端视觉回归。
8. 页面无横向溢出、底部遮挡、点击无响应和不可达控件。
9. 关键操作生成可查看的本地事件或审计记录。
10. 文案、角色和产品定位保持一致：让每一个 KOL 创作并运营属于自己的 Agentic Playable。

## 7. 需要产品确认的关键决策

在继续全量开发前，需要确认以下范围，避免前端演示与未来真实能力冲突：

1. 移动端默认继续使用 Mock，还是默认连接本地服务、失败后回退 Mock。
2. 第一版 AI 分身是否仅做资料、人格、能力和渠道的前端演示，还是需要接入真实模型。
3. 第一版是否纳入真实 KYC、真实社交渠道连接和链上钱包。
4. 五人节点第一版只做协作关系，还是同时定义经济节点、奖励和退出规则。
5. 第一版目标用户优先级：KOL 创作者、普通体验用户、品牌方、审核/运营人员。
6. 第一版语言范围：仅简体中文，还是同时完成英文。
7. 第一版发布范围：本地产品演示、可内部测试版本，还是面向公开用户的生产版本。
